## 2. 技术选择

以下为 001 plan 提出的技术方向，来自 [PRD.md](../../docs/PRD.md) 的已确认选择与 §4.1 的拟采用方案；不表示已经安装、锁定或批准。具体版本、依赖 patch 与锁文件由对应实施 spec 的验收记录确定，001 不虚构 pin。

| 领域 | 计划选择 | 理由 | 负责版本与验收出口 |
|---|---|---|---|
| Python 运行时 | Python >=3.11，`uv` 管理工作区 | 用户已确认的 Python 与 uv 方向；单一工具链减少环境分叉 | 002 建立可运行环境并保存命令与退出码 |
| 服务端框架 | FastAPI、Pydantic、SQLAlchemy、psycopg、Alembic | 与 PRD §4.1 的短事务 API、数据模型与迁移方向一致 | 002 建立最小服务；后续版本按域扩展 |
| 业务存储 | PostgreSQL，ltree／JSONB 表达层级与扩展字段 | 图与业务记录共享数据库，不引入消息中间件 | 002 初始化；008–010 定稿图模型 |
| worker 本地状态 | SQLite、受限工作目录、子进程管理 | 事务记录领取、事件队列与恢复状态 | 011 完成队列、租约与恢复 |
| Web 界面 | Next.js App Router、TypeScript、React Flow、ECharts | 用户已确认的自研界面方向；图与统计有明确组件 | 002 最小页面；006–009、022–030 扩展 |
| 身份 | OAuth2／OIDC Authorization Code＋PKCE | 凭据由身份提供方处理，Protostar 管理自身用户与权限 | 015–017；002 不启用远程身份 |
| MCP | 官方 Python SDK，stdio 与 Streamable HTTP | 复用同一业务操作与权限检查 | 019 |
| 执行后端 | OMP、Hermes、Codex 官方 CLI／SDK／事件接口 | 按任务路由并保留原生 session 标识 | 002（OMP 单任务）、012、013、014 |
| 知识 | Hindsight 官方 API／客户端 | 知识正文由 Hindsight 负责，Protostar 只存绑定与权限 | 022–024 |
| 代码理解 | CodeGraph CLI／MCP | 索引位于代码工作区，查询附代码版本 | 025 |
| 分类 | Jev Python SDK＋可配置结构化小模型 | 统一分类结果，不绑定单一供应商 | 026 |
| 测试 | Test-First，框架与命令由各实施 spec 决定 | constitution IV 要求真实、可重复、隔离的检查 | 002 起每个 spec 的验收记录 |

## 3. 模块与协议权威模型

| 对象类别 | 唯一权威 | 其他角色 | 依据 |
|---|---|---|---|
| 用户、组织、成员、项目、需求、产物版本、审批 | `protostar_server` | CLI、MCP、skills、GUI 经 server 操作 | [PRD.md](../../docs/PRD.md) §4.3、§9 |
| 节点、边、图变更序列、任务派发、领取租约 | `protostar_server` | worker 只能领取与回报，不写业务图 | PRD §4.3、§7.1、§8.1 |
| 运行投影、事件历史、审批记录 | `protostar_server` | worker 提供活会话与原始事件 | PRD §8.2 |
| 活进程、后端 session、本地队列与恢复状态 | `protostar_worker` | server 保存投影，不接管本机进程 | PRD §4.3、§7.4 |
| 知识正文与派生图 | Hindsight | server 保存 bank 映射与访问范围 | PRD §10 |
| 代码索引与查询结果 | CodeGraph（worker 侧调用） | server 只保存查询引用与版本 | PRD §11 |
| 界面状态 | `protostar_gui` 仅展示 | 不建立第二份业务状态或跨组织缓存 | PRD §4.3、§9.2 |

协议不变量：一次工作由带尝试编号的领取租约承担；事件先写本地、再回传并按确认位置清理；失去租约的旧尝试不能回写完成或覆盖新尝试，server 以尝试标识与 fencing 信息拒绝过期报告；同一项目的业务写入只有 server 接受。wire format、端点、字段与超时由 007、010、011、027 定义并验收；001 只记录不变量，不定义接口。

## 4. 计划与实施边界

- 001 plan、research、data-model、contracts、quickstart 均为规划记录，不含业务代码、DDL、运行 API、安装脚本或测试。
- 001 tasks 只能派生规划核对、字段完整性、链接与证据一致性工作，不派生产品实现；tasks 未生成。
- 各实施 spec（002–031）拥有代码、schema、接口、UI、测试、锁文件与真实运行证据；001 不预先替代其 plan 或 tasks。
- 001 不发布功能版本；版本从 002 的 `0.1.0` 开始，与 spec 编号一一对应。
- 任何“已实现”“已运行”“已发布”结论必须由对应实施 spec 的真实输出支持；本计划不产生此类结论。

## 5. 引导期与版本排序

002 使用现有 spec-kit 与人工启动方式准备并批准 spec／plan／tasks，最小系统为本机单操作者、单个活动项目、一项研发需求，服务仅绑定 loopback；由 OMP 执行一个真实获批 task 并显示结果。具体启动命令、进程参数与页面行为归 002 的 plan／tasks，本计划不发明。

排序结论：能力依赖按 PRD §15，发布顺序按 PRD §15.1。W01 在能力上先于 W02，但身份与多组织的实现版本为 015–017；002 以单操作者 loopback 运行，不提前启用远程身份、多组织或跨组织访问。002 真实验收通过、`0.1.0` 获得明确发布批准并形成发布记录后，人工引导期结束；此后 003 起由已运行的 Protostar 承担需求登记、产物审阅、启动获批 tasks 与结果核对。003 的证据用于确认后续自举运行，不作为启动 003 的前置。人工审批持续保留。

## 6. 导入权限与退出规则

- 旧端资料只作行为研究与可选数据导入来源；导入仅在 031 获批后进行，且只接收经批准导出的数据。
- 导入前建立组织、项目、任务、图、会话、运行与外部引用清单，确认归属与权限；无法判定归属的记录停止导入并列出对象，不放入默认公共组织。
- 保留原任务、节点、会话与外部引用标识及历史时间；重复运行不生成重复需求或节点。
- 切换前暂停该项目在旧端的新任务领取，等待在途工作完成或由人类明确终止；冻结并核对记录数量、依赖、产物与未确认报告。
- 切换后同一项目的 Pipeline／PM 写入只有 `protostar_server` 接受；worker、CLI、MCP、skills、GUI 同步指向新服务；旧端移除写入入口、调度与凭据，历史只读留存。
- 失败时停止新任务派发并保留实际变更记录，由人类决定修复或受控恢复；不自动重放有远端副作用的操作。
- 本仓当前没有旧端进程，因此不存在当前停机窗口；只有 031 获批后才发生项目级切换，且不得长期双写。
