## 角色

| 角色 | 职责 |
|---|---|
| 维护者 | 决定产品方向与版本边界；审阅并合并改动；批准发布；保存审批与发布记录；协调安全报告；解释本文件 |
| 贡献者 | 提交 Issue、讨论与 Pull Request；遵守[贡献指南](contributing.md)与[安全策略](security.md) |
| 评审者（按需） | 由维护者针对具体改动邀请，提供技术或文档意见；不因评审自动获得合并或发布权 |

项目不设隐藏角色，也不要求贡献者属于任何组织、使用特定内部系统或承担未经说明的义务。维护者新增或变更应通过公开记录宣布；继任安排在本文件正式批准时补充。

## 决策方式

1. 优先公开讨论，尽量在 Issue、Discussion 或 Pull Request 中形成可核查的理由与结论。
2. 无法达成一致时，由维护者根据项目范围、用户影响与已批准需求作出决定并说明理由。
3. 错字、格式、失效链接与文档澄清由维护者审阅后合并，不要求完整设计流程。
4. 功能、产品行为、版本边界、数据或权限模型的变更，应先公开说明目标与影响，经维护者批准后实施，并记录到对应 Issue／PR 与版本记录。
5. 维护者主导的实现工作遵循 spec → plan → tasks 的逐层批准顺序；外部贡献者的文档修复不等同于实现变更，也不因此被要求套用内部产物模板。
6. 影响项目范围、发布或许可的决定必须公开记录；不以私下沟通替代公开决定。

## 版本与发布

- 001 是需求总览，不单独发布功能版本。002–031 每个 spec 对应一个可演示、可验收的垂直功能与一个 MINOR 版本（`0.1.0` 至 `0.30.0`）。
- 每个版本需要已批准的 spec、plan、tasks，以及真实验收与发布记录；合入、发布与关单保留显式人类授权，维护者之外的 Agent 或服务身份不能代替人类批准。
- 版本采用 `MAJOR.MINOR.PATCH`；002–031 验收发布后提升 MINOR，PATCH 仅用于已发布版本的紧急缺陷修复。
- 不为空目录、脚手架或未完成能力发布版本号。版本计划或编号调整应公开说明，并以更新后的需求与路线记录为准。
- 已发布版本保留对应批准记录、验收输出与已知问题；不删除不利结果来制造完成印象。
