# 参与贡献

感谢关注 Protostar。项目仍处于初始化阶段：`protostar_server` 尚未创建，五个模块目录为空，仓内没有可运行代码、安装流程或测试命令。当前可以贡献的主要是问题报告、设计讨论与文档改进；代码贡献需等对应版本获批并有实际实现基线后再进行。

## 可以贡献什么

- 报告缺陷、失效链接、文档错误或不一致。
- 提出产品行为、工作流、可访问性与集成方面的建议。
- 修正错字、格式、示例与文档表述，补充清楚的说明。
- 参与公开讨论，帮助澄清需求范围与验收方式。

## 公开渠道

使用本仓库公开的 GitHub 渠道：

- **Issues**：缺陷报告、文档问题、功能建议。
- **Pull Requests**：具体的文档或代码改动。
- **Discussions**：开放问题、设计讨论与使用经验（若仓库启用）。

以仓库页面实际启用的功能为准；本文件不假设某个渠道一定开启，也不要求使用外部系统或私有基础设施。讨论与缺陷报告不需要预先审批，没有强制模板；说明清楚即可。如果 Discussions 未启用，用 Issues 提出即可。

## 不同类型的改动

| 类型 | 建议做法 | 审批与记录 |
|---|---|---|
| 错字、格式、失效链接、示例修正 | 直接提交 Pull Request，说明改动范围 | 维护者审阅并合并 |
| 文档澄清或结构改进 | 先提 Issue 或直接提 PR；范围较大时先说明计划 | 维护者审阅并合并 |
| 缺陷报告 | 提 Issue，附复现步骤、期望与实际结果、版本或 commit | 维护者分诊；修复按版本安排 |
| 功能建议或产品行为变更 | 先在 Issues／Discussions 说明问题与目标，取得方向一致后再实现 | 需维护者批准，并纳入对应版本的需求与审批记录 |
| 大范围重构、新模块、数据或权限变更 | 先讨论范围与验收方式，再进入设计 | 需维护者批准；对外部贡献者不强制套用内部文档模板 |

对外部参与者而言，上述只是协作路径，不是额外的审批门槛。维护者会把已接受的产品行为变更记录到对应的版本与需求中；未经讨论的大改动可能无法合并。

## 缺陷报告应包含

- 受影响的模块、版本或 commit。
- 运行环境与复现前提。
- 最小复现步骤。
- 期望结果与实际结果。
- 相关日志、截图或错误信息；提交前移除密钥、token、个人数据与私有代码内容。

能提供更少但可复现的信息，比大段无关日志更有帮助。缺少信息时，维护者可能先在 Issue 中询问。

## Pull Request 期望

- 保持改动聚焦，一个 PR 解决一个清楚的问题；避免顺带修改无关文件或做大面积格式重排。
- 说明改了什么、为什么改、如何验证；涉及行为变化时更新对应文档。
- 关联相关 Issue；没有对应 Issue 的文档修复可以直接说明动机。
- 不提交密钥、凭据、个人数据、生成物或与改动无关的二进制文件。
- 使用清晰的提交说明。项目当前没有既定的构建、测试或格式命令；待实现交付后，以各模块文档中的实际命令为准。

维护者会按可用时间审阅，不承诺响应或合并时限。

## 讨论方式

- 对事不对人，保持技术讨论聚焦于问题、证据与可验证结果。
- 不发布骚扰、歧视、泄露隐私或与项目无关的内容。
- 不重复提交同一问题；补充新证据比新建重复 Issue 更有效。
- 涉及安全漏洞时不要公开细节，按[安全策略](security.md)处理。

项目尚未制定独立的行为准则文件；本节的讨论期望适用于所有公开渠道，后续如需正式准则将由维护者单独提出。

## 安全

不要通过公开 Issue、PR 或 Discussion 披露可利用的漏洞细节、密钥或个人数据。报告方式见[安全策略](security.md)。

## 许可

参与贡献前请阅读仓库根目录的 [`LICENSE`](../LICENSE)。提交贡献即表示你同意以该许可证发布你的贡献；本文件不改变许可证条款。
